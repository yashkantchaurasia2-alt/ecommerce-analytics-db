# Viva Notes

Short, simple explanations of every file and query, followed by likely viva questions with answers. The numbers come from the saved results in `outputs/`.

> **Yaad rakho** lines are quick Hinglish memory tips.

## Part 1: The project in 30 seconds

An e-commerce database for an Indian online store. It has 12 tables in BCNF: customers, addresses, a 3-level category tree, products, warehouses, stock, orders, order items, payments, coupons, coupon uses and deliveries. The sample data covers 50 customers and 279 orders over 7 months (May–Nov 2026), paid by UPI, card, COD and net banking.

On top of the schema there are SQL files for:
- the four SQL command groups (DDL, DML, DCL, TCL)
- joins, subqueries and set operations
- analytics: repeat customers, best sellers, order and payment analysis
- views, indexes, window functions and CTEs

One test script rebuilds everything from scratch and runs 213 checks.

**Headline numbers:**

| What | Number |
|---|---|
| Net revenue | ₹27,59,323.10 |
| Paid orders | 254 |
| Average order value | ₹10,863.48 |
| Repeat customers | 34 of 44 ordering customers (77.3%) |
| Best seller by units | boAt Airdopes 141 |
| Best seller by revenue | OnePlus 12R |

> **Yaad rakho:** "Revenue" ka matlab hamesha *SUCCESS payment, aur order CANCELLED nahi*. Har query yahi definition use karti hai, isliye saare totals match karte hain.

## Part 2: Every file and query, explained simply

### `sql/01_ddl_schema.sql`: building the tables (DDL)
- **What it builds:** 12 tables with primary keys, foreign keys, UNIQUE, NOT NULL, CHECK and DEFAULT constraints.
- **Price at purchase:** `order_items.unit_price` keeps the price the customer actually paid, so later price changes do not rewrite old orders.
- **No stored order total:** the total is always calculated as `SUM(quantity * unit_price)`, so it can never disagree with the items.
- **Composite FK:** an order can only ship to an address that belongs to the same customer.
- **ALTER:** adds the `mrp` column, changes `brand` to NOT NULL, and adds the "MRP ≥ price" CHECK.
- **RENAME, TRUNCATE, DROP:** shown on a throw-away table.

> **Yaad rakho:** TRUNCATE ek DDL command hai. Yeh auto-commit hoti hai, isliye rollback nahi hoti. DELETE ek DML command hai, aur uska rollback ho sakta hai.

### `sql/02_dml_seed_data.sql`: sample data (INSERT)
- **What it holds:** 1,724 realistic rows, generated by `tools/generate_seed.py` with a fixed random seed, so the data is the same every time.
- **Variety built in:** some customers never ordered, some order a lot, some products never sold, and some payments failed or are still pending.

### `sql/03_dml_operations.sql`: UPDATE, DELETE, SELECT

| What | Explanation |
|---|---|
| UPDATE boAt prices +5% | Old orders keep their old price |
| UPDATE with a subquery, then UPDATE … JOIN | Confirms the oldest pending UPI payment and its order |
| UPDATE restock | Bhiwandi rows below the reorder level get +50 |
| INSERT then DELETE | A spam customer and a test coupon are removed; real data is not touched |
| 7 SELECTs | WHERE + ORDER BY, GROUP BY, HAVING (categories with ≥ 3 products), BETWEEN + LIKE |

### `sql/04_dcl_users_roles.sql`: who may do what (DCL)
- **Roles:** 3 roles are created, then 3 users. Each user gets its role and a default role.
  - `db_admin`: everything.
  - `order_clerk`: reads reference tables and inserts/updates orders. It can update only the `quantity` column of inventory (a column-level privilege) and can never delete.
  - `analyst`: read-only, later views-only.
- **REVOKE demo:** DELETE on orders is granted to the clerk by mistake, then revoked.
- **Passwords:** MySQL generates random passwords, so no password is ever written in the repo.

### `sql/05_tcl_transactions.sql`: transactions (TCL)

| Case | What happens | Result |
|---|---|---|
| 1 | Order → items → stock − → payment → delivery → **COMMIT** | Stock fell by exactly the ordered quantity |
| 2 | Same steps, then the payment fails → **ROLLBACK** | Stock was 118 inside the transaction and 121 after ROLLBACK |
| 3 | 500 phones wanted, `WHERE quantity >= 500` matches 0 rows → **ROLLBACK** | Nothing changed |
| 4 | Item 1 → **SAVEPOINT** → item 2 is out of stock → **ROLLBACK TO SAVEPOINT** → COMMIT | The order keeps only item 1 |
| 5 | `SET autocommit = 0` → change → ROLLBACK undoes it. `autocommit = 1` → ROLLBACK cannot undo | Both shown |
| Procedure | `sp_place_order` decides by itself: no stock or failed payment → ROLLBACK, else COMMIT. `FOR UPDATE` locks the stock row; an EXIT HANDLER rolls back on any error | 3 calls give 3 different results |

> **Yaad rakho:** Order IDs mein gap (1277 ke baad 1280) isliye hai kyunki rolled-back orders AUTO_INCREMENT number use kar chuke the. Yeh normal hai.

## Part 3: Likely viva questions

**1. What is the difference between 3NF and BCNF?**
- **3NF:** for every FD X → Y, either X is a superkey **or Y is a prime attribute** (part of some candidate key).
- **BCNF:** drops that exception. Every determinant must be a superkey.
- **Example (`docs/normalization.md`):** `courier_coverage(pincode, courier, hub)` with `hub → courier`. The table is in 3NF because courier is prime, but not in BCNF because hub is not a key. The fix is to split it into `hubs(hub, courier)` and `pincode_hubs(pincode, hub)`.

**2. Which anomalies does normalization remove?**
- **Update:** changing a phone number in many rows.
- **Insert:** a product cannot be added until someone orders it.
- **Delete:** deleting the only order loses the customer.

**3. Why is `unit_price` stored in `order_items` when products already have a price?**
- `products.price` is today's price.
- `unit_price` is the price at purchase. It depends on the order **and** the product, so it belongs to the composite key and is not a partial dependency.
- Example: 114 order lines were sold at an older price (the iPhone was ₹72,999 before its price cut).

**4. Why is the order total not stored?**
- It is derived data (`SUM(quantity * unit_price)`).
- Storing it would create redundancy that could drift out of sync with the items.

**5. Primary key vs unique key?**
- A table has only one PK. It cannot be NULL and is used by FKs.
- A table can have many UNIQUE keys, and each one allows NULLs. For example, `transaction_ref` is NULL for COD payments.

**6. What do ON DELETE CASCADE / RESTRICT / SET NULL do here?**
- **CASCADE:** deleting an order deletes its items and payments.
- **RESTRICT:** a customer who has orders cannot be deleted.
- **SET NULL:** if a referrer is deleted, `referred_by` becomes NULL.

**7. DELETE vs TRUNCATE vs DROP?**
- **DELETE:** removes chosen rows, is DML, and can be rolled back.
- **TRUNCATE:** removes all rows at once, resets AUTO_INCREMENT, is DDL, and auto-commits.
- **DROP:** removes the table itself.

**8. What does ROLLBACK do? COMMIT?**
- **ROLLBACK:** undoes every change since START TRANSACTION.
- **COMMIT:** makes the changes permanent.
- Case 2 shows stock at 118 inside the transaction and back at 121 after ROLLBACK.

**9. What is a SAVEPOINT?**
- A named point inside a transaction.
- `ROLLBACK TO SAVEPOINT` undoes only the work after that point, and the transaction continues (Case 4).

**10. Explain ACID with this project.**
- **Atomicity:** an order is all-or-nothing (Cases 2 and 3).
- **Consistency:** CHECK constraints stop stock from going negative.
- **Isolation:** `SELECT … FOR UPDATE` locks the stock row in the procedure.
- **Durability:** after COMMIT the data survives a restart.

**11. GRANT vs REVOKE, and why roles?**
- **GRANT** gives a privilege; **REVOKE** takes it back.
- A role bundles privileges. You give the role to many users, and to change the policy you change one role.

**12. Why use a view?**
- **Simplicity:** one name hides a 6-table join.
- **Security:** the analyst reads the views but gets error 1142 on base tables.
- **Consistency:** one definition of revenue for everyone.
- A view stores no data; its SELECT runs every time it is queried.

**13. When can a view be updated? What is WITH CHECK OPTION?**
- **Updatable:** a single table with no GROUP BY, DISTINCT or JOIN, like `vw_active_products`.
- **WITH CHECK OPTION:** rejects a change that would move the row outside the view, e.g. setting `is_active = FALSE` gives error 1369.

**14. INNER vs LEFT vs FULL OUTER join? How do you do FULL OUTER in MySQL?**
- **INNER:** only matching rows.
- **LEFT:** all rows of the left table, with NULLs where there is no match.
- **FULL OUTER:** all rows of both tables. MySQL has no keyword for it, so write `LEFT JOIN … UNION … RIGHT JOIN` (J6). Use UNION, not UNION ALL, or the matched rows appear twice.

**15. What is a self join?**
- A table joined to itself with two aliases.
- Here: a category and its parent (J7), and the referrer and the referred customer (J9).

**16. Nested vs correlated subquery?**
- **Nested:** the inner query runs once, independent of the outer query (S3).
- **Correlated:** the inner query uses a column of the outer row, so it runs again for every row (S7: `p2.category_id = p.category_id`).

**17. Why is NOT EXISTS safer than NOT IN?**
- If the subquery returns even one NULL, `NOT IN` returns no rows.
- `NOT EXISTS` only checks whether a row exists, so NULLs cannot break it.

**18. UNION vs UNION ALL?**
- **UNION** removes duplicates, which needs extra work. **UNION ALL** keeps them and is faster.
- U3: UNION gives 38 rows, UNION ALL gives 66. The difference of 28 is the customers who appear in both lists, and that equals the INTERSECT result.

**19. MySQL has no MINUS. What do you use?**
- `EXCEPT` (MySQL 8.0.31+).
- On older versions: `NOT EXISTS` or `LEFT JOIN … IS NULL`.
- E1, E1b and E1c give the same 12 customers.

**20. RANK vs DENSE_RANK vs ROW_NUMBER?**

From W1 (Spigen and Portronics both sold 37 units):

| Units | ROW_NUMBER | RANK | DENSE_RANK |
|---|---|---|---|
| 73 | 1 | 1 | 1 |
| 37 | 2 | 2 | 2 |
| 37 | 3 | 2 | 2 |
| 35 | 4 | **4** | **3** |

- ROW_NUMBER is always unique.
- RANK leaves a gap after a tie.
- DENSE_RANK never leaves a gap.

**21. What does PARTITION BY do?**
- It restarts the window calculation for each group.
- `RANK() OVER (PARTITION BY category ORDER BY units DESC)` ranks products inside each category (W2).

**22. Why can't a window function go in WHERE?**
- Window functions are calculated after WHERE, GROUP BY and HAVING.
- To filter on a rank, compute it in a CTE first and filter outside (W2b, W3).

**23. What is a CTE? Why use it instead of a subquery?**
- `WITH name AS (…)` is a named, temporary result for one statement.
- It reads top to bottom and can be used more than once.
- T3 does in one CTE what S14 needed two copies of a derived table for.

**24. How does a recursive CTE work?**
- **Anchor:** the starting rows (top-level categories).
- **UNION ALL.**
- **Recursive part:** joins back to the CTE itself to go one level deeper.
- It stops when no new rows appear. The `level < 10` guard protects against loops.

**25. What is an index, and what is the trade-off?**
- An index is a sorted B+ tree on a column, like a book's index: MySQL jumps to the rows instead of scanning them all. X1 went from 312 rows read to 3.
- **Trade-off:** every INSERT, UPDATE and DELETE must also update the index, and it uses disk space. So index only the columns that appear in WHERE, JOIN or ORDER BY.

**26. How do you read EXPLAIN?**
- **type:** ALL (full scan), range, ref, const. Further right is better.
- **key:** the index used.
- **rows:** the estimated rows read.
- **Extra:** "Using filesort" means an extra sort was needed.

**27. Why was an index not used in X4?**
- `YEAR(order_date) = 2026` wraps the column in a function, so the sorted index cannot be used.
- Write `order_date BETWEEN '2026-01-01' AND '2026-12-31'` instead.

**28. What is the composite-index leftmost-prefix rule?**
- `(status, method)` helps queries on `status`, or on `status` and `method` together.
- It does not help a query on `method` alone.

**29. How do you know the results are correct?**
- `tests/run_tests.py` rebuilds the database and runs 213 checks.
- Each important result is cross-checked against an independently written query. For example, EXCEPT = NOT EXISTS = LEFT JOIN IS NULL, and revenue by method = revenue by month = total.

**30. Where are the passwords?**
- **DB password:** only in `.env`, which is git-ignored. The repo has `.env.example` with empty values.
- **Project users:** created with `IDENTIFIED BY RANDOM PASSWORD`, so no password is ever written in a file.
