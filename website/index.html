Design decisions

  • Price at purchase. order_items.unit_price keeps what the customer paid, so later price changes never rewrite history.
  • No stored totals. Order totals are derived with SUM(quantity × unit_price), so they can never drift out of sync.
  • Composite FK. An order can only ship to an address belonging to the same customer, and the database enforces it.
  • Two self-references. categories.parent_category_id (tree) and customers.referred_by (referrals), used for self joins and recursive CTEs.
  • 1:1 delivery. UNIQUE(order_id) on deliveries.
  • Safe defaults. CASCADE for child rows, RESTRICT to protect history, SET NULL for referrers.

Design theory

From one messy sheet to BCNF

The full walkthrough with every functional dependency is in docs/normalization.md. Here is the short version.

  1. UNF

    One big order sheet

    Customer details repeated on every order, product lists packed into one cell. Changing a phone number means editing many rows (update anomaly); a product can't exist until someone buys it (insert anomaly); deleting the only order loses the customer (delete anomaly).

  2. 1NF

    Atomic values

    One row per (order, product). Key: (order_id, product). Note unit_price depends on the order and the product: the same phone case sold for ₹499 and ₹449.

  3. 2NF

    No partial dependencies

    order_id → date, customer, … and product → category depend on half the key, so orders, products and order_items become separate tables.

  4. 3NF

    No transitive dependencies

    order_id → email → name, phone and coupon_code → percent are pulled out into customers, discounts and categories. Payments get their own table because one order can have several attempts.

  5. BCNF

    Every determinant is a key

    courier_coverage(pincode, courier, hub) with hub → courier is in 3NF (courier is prime) but not BCNF (hub is not a key). Split into hubs(hub, courier) and pincode_hubs(pincode, hub): lossless, at the cost of one dependency no longer being checkable in a single table.

Result: all 12 tables in the real schema are in BCNF. Every non-trivial FD has a key (PK or UNIQUE) on its left side.
